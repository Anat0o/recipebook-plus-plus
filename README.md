# RecipeBook++

Справочник крафтов и способов добычи Minecraft: статический сайт для GitHub Pages.
По любому предмету показывает **все** способы его получить — верстак, печь, плавильня,
коптильня, костёр, камнерез, кузнечный стол, выпадение с мобов и из блоков, сундуки
структур, рыбалку, бартер, археологию и торговлю с жителями — и обратный список
«где предмет используется».

Данные берутся из [misode/mcmeta](https://github.com/misode/mcmeta) — версионированной
истории сгенерированных данных и ассетов Minecraft — и целиком предрассчитываются
на этапе сборки: бэкенда у сайта нет.

## Как это устроено

| Слой | Что делает |
|---|---|
| `tools/` | Пайплайн данных: выгрузка mcmeta, разбор рецептов, интерпретатор таблиц добычи, рендер иконок, шардирование |
| `src/lib/` | Загрузка данных, поиск, роутер, названия источников |
| `src/ui/mc/` | Интерфейс: сетка верстака, слоты, спрайты, баннеры, 3D-постройки, таб-бар, шит, сегменты, слайдеры |
| `src/lib/webgl.ts` | Свой рендер построек: геометрия, орбитальная камера, шейдеры |
| `tools/curated/guides/` | Гайды по автофермам и редстоуну: материалы, шаги, схемы |
| `public/data/` | Результат сборки (в репозиторий не коммитится) |

Оформление целиком повторяет GUI игры: панели со скосами, пиксельный шрифт, фон
из еловых досок. Текстур интерфейса в данных игры нет (в атласе только блоки,
предметы и существа), поэтому рамки и кнопки рисуются CSS — заодно они остаются
чёткими при любом масштабе.

От iOS остались не картинки, а поведение: детенты и грабер шита, свайп для закрытия,
зоны нажатия не меньше 44 pt, поддержка «Уменьшения движения» и «Понижения
прозрачности». Пиксельная кнопка нажимается ровно так же удобно, как стеклянная,
и это закреплено тестами в `tests/a11y.spec.ts`.

Контраст текста считается по токенам темы, а не проверяется на глаз:
`src/styles/contrast.test.ts` падает, если любая пара «текст на панели»
опускается ниже 4.5:1 или кегль становится мельче 12 px. Пиксельный шрифт к
этому чувствительнее обычного — тонкие штрихи пропадают раньше.

### Иконки

Атласы mcmeta содержат сырые текстуры, а не готовые иконки инвентаря, поэтому блоки
рендерятся изометрией на этапе сборки: `tools/mc/models.ts` разворачивает цепочку
`parent` моделей, `tools/mc/render.ts` растеризует грани с z-буфером и ванильной
таблицей затенения, применяя display-трансформацию `gui` (поворот `[30, 225, 0]`).
62 предмета (сундуки, шалкеры, знамёна, головы) игра рисует своим кодом — для голов
геометрия задана вручную, остальные помечены в интерфейсе как приблизительные.

### Гайды и схемы

Разделы «Автофермы» и «Редстоун» — это 28 гайдов, описанных данными
(`tools/curated/guides/`), а не вёрсткой. Каждый гайд знает свои материалы,
порядок сборки, оговорки и издания, на которых схема работает как описано.

**Скриншотов из игры здесь нет и не будет** — клиента Minecraft у сборки нет,
а выдавать чужие снимки за свои нельзя. Вместо них трёхмерная модель постройки
с настоящими текстурами и моделями блоков: её можно вращать и приближать,
у каждого шага сборки свой вид, и есть отдельный вид готового результата.
На готовой схеме работают рассчитанный редстоун, сущности и сценарии роста/лута;
доступны «Пуск», ручной кадр, сброс, три скорости и прозрачный режим разреза.
На шаге новые блоки плотные, поставленные раньше — полупрозрачные.

Так же устроены многоблочные постройки (`tools/curated/multiblocks.ts`) —
призыв Визера, големы, маяк, портал. В рецептах их нет: форму проверяет код
игры. Постройка появляется в разделе «Использование» у каждого участника,
поэтому голова визер-скелета рассказывает про Визера, а блок железа — про
голема и маяк.

### Как устроен 3D

Модели разбираются **на сборке**, а не в браузере: `tools/build-blocks.ts`
разворачивает цепочки `parent`, считает UV и повороты элементов и складывает
готовые грани в `blocks.json` (47 КБ) плюс атлас только из нужных текстур
(25 КБ). Браузеру остаётся залить вершины и крутить камеру.

Рендер свой, без библиотеки (`src/lib/webgl.ts`, около 400 строк). Геометрия —
осепараллельные коробки с готовыми UV, свет — четыре константы яркости граней
из игры, камера — орбита. Это +3,7 КБ к бандлу против ~150 КБ у three.js,
которая удвоила бы весь сайт. Текстуры фильтруются `NEAREST`: пиксель в пиксель.

Сетка слоёв осталась удобным способом писать постройку руками, но ячейка теперь
несёт направление и шаг: `piston^west@3`. Направление обязательно для поршней,
наблюдателей и воронок — на это стоит тест, потому что неповёрнутый поршень в
схеме выглядит правдоподобно и молча учит неправильному.

**Сам поворот берётся из блоксостояний игры** (`tools/mc/blockstates.ts`), а не
из таблицы в коде, и применяется со сменой знака: у игры углы отсчитываются в
другую сторону, чем у `rotateAxis`. Без этого восток менялся местами с западом,
а верх с низом — при верных севере и юге, потому что 0° и 180° от смены знака не
меняются. Ошибка пережила просмотр контрольных листов глазами и всплыла на
такте с воронками, где неправильность видна как смысл: они расходились, хотя
должны сходиться.

Отсюда правило: **направление блока проверяется числом, а не взглядом.**
`tools/build-blocks.test.ts` берёт опознаваемую грань (у печи `furnace_front`,
у наблюдателя `observer_front`, у поршня `piston_top`), считает её внешнюю
нормаль после поворота и требует совпадения с заданной стороной — по всем шести
направлениям. У воронки текстуры-подсказки нет, поэтому сверяется смещение
носика. Со старым знаком этот тест падает двенадцатью проверками.

Второй инвариант: поршень, воронка, наблюдатель, раздатчик и дроппер должны
смотреть на занятую клетку постройки. Механизм, направленный в пустоту, — это
либо неверное направление, либо схема, в которой он ни к чему не подключён;
именно так нашлась развалившаяся ферма арбузов. Первая попытка выписать повороты руками провалилась ровно так,
как и должна была: блоки стояли, но смотрели не туда. В данных игры хватает
неочевидного — у воронки вбок вообще другая модель (`hopper_side`), у раздатчика
вверх своя (`dispenser_vertical`), у повторителя `facing=east` это 270°, а не 90°,
а у двери нулевой поворот вовсе не север, а восток. Каждый из этих случаев теперь
закреплён тестом.

Геометрия печётся на тройку «блок + направление + форма» и приезжает в браузер
уже повёрнутой. Это не оптимизация, а устранение второго источника правды: пока
таблица поворотов жила ещё и в рантайме, ошибиться можно было дважды.

Форма нужна редстоуновой пыли: она тянется к соседней пыли и к приборам, и
именно эти линии показывают, куда идёт сигнал. Соседи считаются по всей
постройке, а какие части рисовать — снова решают данные игры: у провода
девять частей с условиями, и среди них неочевидное правило, что на прямом
участке точка не рисуется, а на повороте рисуется. Условия `when` вычисляются
по блоксостоянию, а не переписаны в код.

Этот же тест поймал два настоящих разрыва в схемах: у RS-фиксатора провод
посередине ни с чем не соединялся, у инвертора вход был одинокой точкой. Плоский редстоун-узел,
умещающийся в один слой, собирается по стадиям: опора, механизмы, провод, вход.

Проверять надо глазами: `npx tsx tools/preview-build.ts` рисует контрольный лист
всех 35 построек по шагам — **тем же растеризатором и той же геометрией**, что
уходят в браузер. Считать превью отдельным кодом нельзя: тогда оно перестанет
быть проверкой.

Три ошибки здесь ловились только пикселями, без единого сообщения в консоли:
обратный порядок умножения матриц (сцена уезжала за кадр), отсечение граней по
обходу (у моделей игры он обратный к принятому в GL) и очистка буфера после
вывода. Поэтому в `tests/build3d.spec.ts` сравниваются настоящие пиксели холста,
а не факт его существования.

### Шум в способах получения

Две чистки, обе на данных, а не на глаз:

- **Самодроп.** 883 источника вида «ломаешь блок — получаешь его же» без единого
  условия не сообщают ничего. Сборка помечает их `selfDrop`, интерфейс прячет —
  но оставляет, если других способов у предмета нет. Таких 94: камень Энда,
  листва, бетон, базальт. Условный дроп остаётся всегда: камень отдаёт себя
  только с шёлковым касанием, и это как раз важно.
- **Только из команд.** 118 предметов не имеют ни одного источника — 88 яиц
  призыва и служебные блоки вроде барьера и командного блока. Они скрыты, а
  переключатель в настройках их возвращает. Признак считается по полному списку
  источников, **до** того как интерфейс спрячет самодроп: перепутать порядок —
  значит стереть из каталога те самые 94 блока.

### Приложение на телефон

Сайт ставится на телефон как приложение: манифест и теги установки генерирует
сборка (иначе базовый путь разъезжается между манифестом, иконками и воркером),
иконки лежат в `public/icons/`. Кнопка в настройках складывает всю версию — около
4 МБ — в кэш, предупреждая, что и iOS, и Android вытесняют данные сайта при
нехватке места. Сайт запрашивает постоянное хранение и честно показывает ответ
браузера: на iOS обычно отказ.

Сервис-воркер собирается из `tools/sw-template.js`, потому что список файлов
оболочки знает только сборка — имена бандлов содержат хеш. Без этого списка
оффлайн открывал бы пустую страницу; на это есть сквозной тест, который рвёт
сеть по-настоящему.

### Баннеры

Ткацкий станок — единственная станция, где картинку нужно собирать самому.
Готовых изображений баннеров нет: `tools/build-banners.ts` вырезает из атласа
чёрно-белые маски узоров (лицевая сторона флага — область 20×40 пикселей) в одну
ленту на 13 КБ, а цвет накладывает браузер через CSS-маску. Поэтому доступны все
16 цветов без пересборки, а каждый слой остаётся отдельным элементом — на этом
держится анимация послойной сборки.

Связь узора с предметом-образцом читается из тегов, а не угадывается по имени:
`field_masoned_banner_pattern` даёт узор `bricks`, а `bordure_indented_banner_pattern` —
`curly_border`. Девятнадцать готовых дизайнов в `tools/curated/banners.ts` проверены
глазами через `npx tsx tools/preview-banners.ts`.

### Вероятности

`tools/mc/loot.ts` считает выпадение не симуляцией, а свёрткой дискретных
распределений (`tools/mc/dist.ts`), поэтому шанс и матожидание точны:
череп визер-скелета — 2,5 % и 5,5 % при Добыче III, алмазная руда с Удачей III —
2,2 алмаза. Эти значения закреплены тестами.

## Команды

```bash
npm install
npm run fetch:fonts    # пиксельный шрифт Monocraft (OFL)
npm run build:data     # выгрузка mcmeta и сборка данных всех версий
npm run check:coverage # отчёт полноты: рецепты, лут, иконки, предметы без источников
npm run dev            # разработка
npm run build          # продакшен-сборка (BASE_PATH задаёт путь GitHub Pages)
npm test               # юнит-тесты вероятностной математики
npm run test:e2e       # сквозные проверки в браузере
```

Собрать данные одной версии: `npm run build:data -- 26.2`.
Посмотреть глазами: `npx tsx tools/preview-icons.ts diamond_ore furnace`,
`npx tsx tools/preview-banners.ts` (готовые дизайны) и `--patterns` (каталог узоров).

## Версии Minecraft

Набор версий задаётся в [`tools/config.ts`](tools/config.ts). Сейчас это 26.2, 26.1.2
и 1.21.11. Для 26.x торговля собирается из `villager_trade`/`trade_set`, а для
1.21.11 используется воспроизводимый снимок из официального server JAR с Mojang
mappings (`tools/legacy/DumpTrades.java`, `tools/extract-legacy-trades.ts`). Вкладка
«Жители» показывает 13 профессий, странствующего торговца, безработного и дурачка,
рабочие блоки, семь биомных обликов и полные пулы предложений.

Workflow `refresh-data.yml` ежедневно сверяется с mcmeta и открывает pull request,
когда выходит новая версия.

## Что ведётся вручную

Не всё в Minecraft описано данными. В `tools/curated/` лежит то, что зашито в код игры:
цвета тонировки и красителей, геометрия голов, дерево варки зелий, готовые дизайны
баннеров и способы получения без таблиц добычи — звезда Нижнего мира с иссушителя,
элитры с корабля Энда, наполнение вёдер, зловещие хранилища. Каждый такой файл помечен полем `VERIFIED_FOR`.
